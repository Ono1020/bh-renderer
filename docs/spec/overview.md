## 0. 目的と、やらないこと

### 0.1 目的

1. ブラックホールの影（シャドウ）、フォトンリング、上下に回り込んで見える降着円盤など、重力レンズによる像を**光線を実際に曲げて**描く
2. 降着円盤は「板にテクスチャを貼ったもの」ではなく、温度・密度・速度場を持つガスとして描く
3. 細かいパーティクル（ガスの塊、デブリ）は、板の上を回る飾りではなく、**時空の測地線に従うテスト粒子**として運動させる
4. カメラをどこに置いても破綻しないこと。静止画だけでなく、将来は動画にも使えること

### 0.2 やらないこと（少なくとも最初の完成までは）

- パーティクル同士の重力（N体計算）。理由は §5.3 で述べる通り、物理的にも正しくない近似になるため
- ガス同士の衝突、磁場、プラズマの計算（GRMHD）。これは EHT の研究用コード（ipole 等）の領域で、個人制作の範囲を超える
- Blender の全メッシュを曲がった光線で描くこと。主役の物体（宇宙船など）に限定する（§6.4）
- リアルタイム描画。オフライン前提でステップ数を稼ぐ

### 0.3 先に決めた設計判断

| 判断 | 選択 | 理由 |
|---|---|---|
| 描画方式 | ピクセルごとの測地線積分（後方レイトレーシング） | 光が曲がる現象はラスタライズでは原理的に扱えない |
| 最初の計量 | Schwarzschild（回転なし） | 検証可能な正解（影の大きさ等）が多数ある |
| 最終目標の計量 | Kerr（回転あり、$a \to 0.99$ 程度） | ガルガンチュアはほぼ極限回転。影の歪みとフレームドラッギングが要る |
| GPU 実装 | Vulkan Compute Shader | BVH・蓄積バッファ・パーティクル SSBO を扱いやすい |
| 円盤モデル | 薄い円盤（平面交差）＋厚みのあるボリューム（レイマーチング）の二層 | 薄い成分が高次像の鋭さを、ボリュームがガスの厚みと霞みを担う |
| 単位系 | 幾何単位系 $G = c = 1$、$M = 1$ | 式が大幅に簡単になる。見た目への換算は最後にスケールするだけ |

### 0.4 言語の内訳（「C」ではなく C++）

ホスト言語は **C++（C++20）** である。純粋な C ではない。Vulkan API 自体が C の API なので資料や関数名は C 風に見えるが、それを使う側の言語は C++ とする。理由は、BVH・ベクトル／行列演算・ファイル読み込みなどをクラスと標準ライブラリで書いた方が、バグが減り検証もしやすいためである。

| 場所 | 言語 |
|---|---|
| レンダラーのホスト側（Vulkan 初期化、glTF/JSON 読み込み、EXR 出力、検証テスト） | C++20 |
| GPU 側の計算（測地線積分、円盤、パーティクル更新） | GLSL（Compute Shader、SPIR-V にコンパイル） |
| Blender アドオン（パネル、書き出し、レンダラー呼び出し） | Python（Blender の標準） |
| Phase 0 の物理プロトタイプ | Python（NumPy）。ここで通した式を GLSL に移植する |

## 1. 全体アーキテクチャ

```
┌──────────────────────────── Blender ────────────────────────────┐
│  カメラ配置 / 円盤パラメータ / 星空HDRI / 主役メッシュの配置       │
│  アドオンのパネル: [プレビュー] [本番レンダー] ボタン             │
└──────────────┬──────────────────────────────────────────────────┘
               │ 書き出し
               │  scene.json（カメラ・物理パラメータ）
               │  scene.glb（主役メッシュのみ）
               │  sky.exr（背景の天球テクスチャ）
               ▼
┌────────────────────── 外部レンダラー (C++ / Vulkan) ─────────────┐
│                                                                  │
│  ① Particle Pipeline (Compute)                                   │
│     測地線でパーティクル位置を更新 → SSBO                        │
│  ② Geodesic Pipeline (Compute) ← 本体                            │
│     ピクセルごとに測地線を積分し、円盤・粒子・メッシュ・         │
│     星空との出会いを記録 → 蓄積バッファ (RGBA float)             │
│  ③ Post Pipeline (Compute)                                       │
│     蓄積平均 → トーンマップ → EXR / PNG 出力                     │
│                                                                  │
└──────────────┬──────────────────────────────────────────────────┘
               │ render_0001.exr
               ▼
        Blender のコンポジターで読み込み、色調整・合成
```

ポイントは、Blender はあくまで「置く場所」であって「描く場所」ではないこと。
逆にレンダラー側は Blender のマテリアルを一切解釈しない。物理パラメータだけを受け取る。

## 2. 単位系と座標系

### 2.1 幾何単位系

$G = c = 1$ と置き、ブラックホールの質量を $M = 1$ とする。このとき長さの単位は $r_g = GM/c^2 = 1$ で、

- シュバルツシルト半径（事象の地平面）: $r_s = 2M = 2$
- フォトン球: $r_{ph} = 3M = 3$
- 影の臨界インパクトパラメータ: $b_{crit} = 3\sqrt{3}\,M \approx 5.196\,M$
- 安定円軌道の最内縁（ISCO）: $r_{ISCO} = 6M$（Schwarzschild）

実際の天体に換算したい場合は最後に $r_g$ を掛けるだけなので、コード内では常に $M=1$ でよい。

### 2.2 座標系

- 計算座標: Boyer–Lindquist 座標 $(t, r, \theta, \phi)$。Kerr まで同じコードで扱えるため
- シーン配置座標: Blender の直交座標 $(x, y, z)$。変換は $x = r\sin\theta\cos\phi$ など標準的なものを使うが、Kerr では厳密には楕円体座標になる点に注意する（描画上の配置変換としてのみ使うので実用上は問題ない）
- ブラックホールの自転軸 = ワールドの $z$ 軸、円盤 = 赤道面 $\theta = \pi/2$
